# 决策记录

## D-001 Android 与 Kotlin

- 状态：已接受
- 决策：Android 原生、Kotlin、Jetpack Compose；最低 Android 8（API 26）。
- 原因：本地优先、长期维护和后续设备能力接入更稳定。

## D-002 首个历法引擎

- 状态：已接受
- 决策：Stage 0 使用 Tyme4j 1.5.1；后续可用另一独立实现做差异测试，但不能形成第二业务入口。
- 原因：其公开 API 覆盖八字、节气、起运与大运，且有可引用的公开测试样本。

## D-003 全局状态隔离

- 状态：已接受
- 决策：Tyme4j 的 `ChildLimit.provider` 在进程级锁内临时切换，并在 `finally` 恢复。
- 原因：避免不同计算配置在并发或异常场景下互相污染。

## D-004 黄金样本隐私

- 状态：已接受
- 决策：仓库只保存公开库样本和人工构造的边界样本；真实问真案例不进入 Git。
- 原因：测试可复现，同时不扩大个人敏感信息暴露面。

## D-005 Room 与版本化协议

- 状态：已接受
- 决策：命例持久化使用 `core:data` 的 Room Schema v2；领域对象以 Kotlin
  Serialization 的显式协议写入 JSON 列，关键检索字段单独建列和索引。
- 原因：保留强类型领域模型和可回导协议，同时避免 Stage 1 过早展开大量易漂移列。

## D-006 恢复安全边界

- 状态：已接受
- 决策：Stage 1 完整恢复只允许空库；所有文件先解压到临时区，校验路径、大小、
  SHA-256、数量和引用后再提交。附件提交失败时清除本次空库写入。
- 原因：在冲突策略和跨资源崩溃恢复尚未完成前，禁止无范围覆盖已有资料。

## D-007 明文备份不伪装加密

- 状态：已接受；密码实现由 D-025 与 D-027 扩展
- 决策：调用方必须明确确认敏感明文导出；密码模式必须生成对应的认证加密容器，任何
  不支持或失败都结构化拒绝，绝不降级为明文。
- 原因：命例包含出生、健康、婚姻、财务和来源图片，误报加密风险不可接受。

## D-008 暂留 Room 2.6.1

- 状态：已接受，待工具链升级时复评
- 决策：Stage 1 使用已通过迁移和恢复测试的 Room 2.6.1，不在本阶段升级到 2.8.4。
- 原因：Room 2.8.4 的 KSP Schema 导出与当前 Kotlin 2.0.20 序列化处理链发生 ABI
  冲突；单独升级 Room 会把当前任务扩大为 Kotlin/KSP/AGP 工具链迁移。

## D-009 Stage 2 使用轻量组合根

- 状态：已接受
- 决策：`NanfengBaziApplication` 的 `DefaultAppContainer` 负责组装 Room
  `CaseRepository` 和 Tyme4j `BaziEngine`；页面只依赖 `StageTwoViewModel`，
  手动新建由 `CreateCaseUseCase` 串联校验、计算和保存。
- 原因：项目当前没有既有依赖注入框架；轻量组合根能保持唯一业务入口，同时避免
  为最小闭环引入额外框架和维护成本。

## D-010 Stage 2 只开放已支持的公历民用时

- 状态：已接受，能力扩展时复评
- 决策：Stage 2 表单只暴露公历、北京时间民用时和手动命例；农历、地区经纬度与
  真太阳时在领域与引擎完成对应能力前不做静态入口或静默降级。
- 原因：真实可操作且失败可解释优先于展示未接通的 v1.0 字段；最终范围不缩小，
  未实现项进入逐条需求差距清单继续推进。

## D-011 编辑出生资料生成新计算快照

- 状态：已接受
- 决策：编辑别名、姓名、性别或出生资料时统一重新调用 `BaziEngine.calculate()`；
  所有旧快照保留但取消采用，新结果追加为已采用快照。保存仍携带打开详情时的期望修订号。
- 原因：不能用页面字段覆盖历史计算证据；修订号和快照序列共同提供并发与算法追溯。

## D-012 记录与事件仍按命例聚合修订

- 状态：已接受，记录级历史已落地
- 决策：Stage 3A 的文本记录和事件增改删通过 `CaseRepository.save()` 原子更新整个
  `BaziCase` 聚合，并在同一事务追加记录级版本，保留子项稳定 ID、来源附件、创建时间
  和列表顺序。页面只读取聚合历史，不自存副本。
- 原因：沿用 Stage 1 唯一增量写入口和事务边界；历史属于领域事实，必须随 Room 和
  完整备份一起往返，不能依赖页面状态或仅靠整例 revision 推断。

## D-013 最近查看不参与聚合修订

- 状态：已接受
- 决策：`lastViewedAt` 由 `CaseRepository.markViewed()` 单列更新，不修改
  `updatedAt` 或 revision；收藏、置顶、分组和标签仍通过带期望修订号的
  `CaseRepository.save()` 更新完整聚合。
- 原因：打开详情是阅读行为，若提升 revision 会让同时打开的合法编辑无故冲突；
  其余管理元数据是用户明确修改，仍需并发保护和备份一致性。

## D-014 列表查询由 Repository 统一解释

- 状态：已接受，规模增长时复评
- 决策：列表只提交 `CaseSearchRequest`；`RoomCaseRepository` 统一完成姓名、别名、
  四柱搜索，分组/标签筛选，置顶优先和排序。当前个人本地规模采用事务内聚合组装，
  不在页面复制规则或提前引入 FTS。
- 原因：保持一个可测试事实入口并优先低维护；若真实规模出现性能证据，再以保持
  同一公共契约的方式增加索引或 FTS。

## D-015 Room Schema v3 管理元数据兼容迁移

- 状态：已接受
- 决策：Schema v3 为 `cases` 增加收藏、置顶和最近查看列；迁移默认值保持旧记录
  语义，序列化实体也提供默认值以兼容备份格式 v1。
- 原因：不改变空库恢复和备份封套即可增加查询字段，避免破坏 Stage 1 数据。

## D-016 整例删除采用可恢复软删除

- 状态：已接受；永久物理清理另行复评
- 决策：整例删除只写入 `deletedAt` 并进入回收站，完整聚合、来源证据和附件文件均
  保留；回收站支持恢复，当前不自动过期或物理清理。
- 原因：命例和来源图片属于高敏感长期资料。在没有用户可验证备份、附件引用计数和
  崩溃恢复日志前，物理删除无法提供与风险相称的恢复保证。

## D-017 命例复制采用研究副本语义

- 状态：已接受
- 决策：复制生成新命例 ID、新计算快照 ID 和 `copiedFromCaseId`，保留出生资料、
  分类和计算结果；不复制记录、事件、来源附件或字段证据，并在完成反馈中明确范围。
- 原因：该语义支持出生时间或规则研究，又避免重复敏感长文本和共享附件路径造成
  删除、备份与来源身份歧义。

## D-018 重复提示不自动裁决

- 状态：已接受
- 决策：Repository 统一按出生时间加性别、已采用四柱分别生成候选与理由，新建和
  编辑在第一次保存前提示；候选包含回收站位置，只有用户明确确认才继续写入。
- 原因：同柱不等于同一人，同名更不能作为身份。候选是核对证据，不是自动合并规则。

## D-019 Room Schema v5 保存记录级历史

- 状态：已接受
- 决策：Schema v5 为当前文本记录增加可空分析分类，并新增文本记录、关键事件两张
  历史表。历史表只外键关联命例，不外键关联当前条目，因此当前条目删除后历史仍保留。
  备份格式继续为 v1，在 `notes.json`、`analysis.json`、`events.json` 内增加带默认空值
  的历史数组和 manifest 计数。
- 原因：这既保持旧版备份可读，又避免把历史嵌入当前行后被覆盖；Schema 版本负责数据
  库兼容，备份字段默认值负责文件协议向后兼容。

## D-020 关键事件标题与类别进入事件快照

- 状态：已接受
- 决策：关键事件增加可选标题和八类结构化类别；字段直接属于 `CaseEvent`，因此当前值、
  事件版本快照、Room JSON 和备份 v1 共同往返。新字段提供默认值，旧数据库与旧备份按
  无标题、综合类别读取，不为仅增加 JSON 默认字段提升 Room Schema 或备份格式版本。
- 原因：标题和类别是事件事实而非界面标签，必须随历史保真；默认值兼容可避免没有必要的
  文件协议和数据库迁移，同时保持旧资料可读。

## D-021 单命例 JSON 先固定零写入交换合同

- 状态：已接受，提交策略待后续增量
- 决策：单命例格式 v1 直接封装完整 `BaziCase`，记录格式/App/数据库版本、ISO 导出时间、
  `REFERENCES_ONLY` 附件模式和规范载荷 SHA-256。导入第一步只做 16 MiB 有界读取、严格
  解码、版本/哈希/领域校验和本地冲突查询，不提供隐式写入。
- 原因：先固定可验证文件事实，才能安全设计跳过、保留两份、模块合并和逐字段采用；
  单 JSON 不携带图片二进制，必须显式暴露该限制，避免生成数据库引用存在但文件缺失的
  伪完整导入。

## D-022 系统文件选择只提供流，预览保持零写入

- 状态：已接受
- 决策：Android 使用 `CreateDocument(application/json)` 和 `OpenDocument` 取得用户选择
  的输出/输入流；ViewModel 在 IO 调度器调用唯一交换服务，并只把成功、错误或预览模型
  回传 Compose。预览弹窗仅显示来源、计数、附件限制和合并后的冲突理由，不提供伪造的
  “继续导入”按钮。
- 原因：系统文件选择解决可访问位置与权限，不应复制协议规则；在冲突决策和附件事务
  尚未完成前维持零写入，能让真实文件链路先被设备验证而不扩大数据损失面。

## D-023 先开放跳过与保留两份，提交时复查冲突

- 状态：已接受
- 决策：单命例导入保持两阶段。第一阶段只读预览；第二阶段先重新查询稳定 ID、出生输入
  和四柱冲突，若候选与预览不同则返回 `PREVIEW_STALE`。当前仅开放“跳过”和“保留
  两份”：前者零写入，后者为命例、记录/历史、事件/历史、快照、分组和标签重建 ID，
  记录 `copiedFromCaseId`，再由 `CaseRepository.save(expectedRevision=0)` 原子创建。
  `REFERENCES_ONLY` 文件存在附件引用时返回 `ATTACHMENT_BINARIES_REQUIRED`。
- 原因：这两种决策不需要覆盖既有事实；提交前复查可防止用户查看预览后本地数据变化，
  原子新建可保证失败不留下半个聚合。禁止附件引用提交，避免数据库声称证据存在但图片
  文件实际缺失。模块/字段合并需要更细的差异模型和历史语义，不能伪装成已完成。

## D-024 模块只追加，替换必须逐字段选择

- 状态：已接受
- 决策：无附件单命例的模块合并仅追加来源独有的计算快照、文本记录/历史、事件/历史、
  分组和标签；以内容签名去重，新增子项重建 ID，来源快照强制为未采用。别名、姓名、
  来源类型、出生输入与性别口径、职业/学历/财务/婚姻/健康、收藏和置顶生成逐字段差异，
  默认保留本地，只有用户选择来源才替换。方案同时保存目标 revision 与规范载荷哈希；
  提交前复查来源冲突和目标事实，回收站目标要求先恢复。
- 原因：追加模块不会删除本地事实，而标量替换可能改变身份和研判口径，必须把范围与
  前后值展示给用户。revision 加载荷哈希能捕获不提升修订号的最近查看等变化，避免用
  过期方案覆盖新状态；计算快照不自动采用可防止导入文件静默改变当前排盘口径。

## D-025 单命例密码容器独立版本化

- 状态：已接受；完整备份密码容器由 D-027 独立实现
- 决策：单命例密码保护使用独立容器版本 1。导出以 PBKDF2-HMAC-SHA256、600,000 次
  迭代和 16 字节随机盐派生 256 位密钥，再使用 AES-256-GCM、12 字节随机 nonce 与
  128 位认证标签保护原单命例 v1 JSON；容器类型、版本、KDF、迭代次数和密码算法进入
  AAD。导入只接受 100,000～2,000,000 次迭代，解密后必须重新执行原格式、Schema、
  载荷哈希与领域校验。无密码单独提示输入；错误密码、篡改和不受支持参数不泄露细节。
  密码与可恢复密钥不写入容器、Room、日志或持久状态，调用链中的私有字符数组用后清零。
- 原因：单命例交换已经具备真实系统文件入口，可先以独立、可演进的认证加密容器满足
  敏感资料便携需求；它不应等待完整 ZIP 的附件事务和批量恢复设计，也不能与 ZIP 格式
  共享未经定义的加密语义。参数上下限同时防止弱 KDF 降级与恶意超量计算。

## D-026 完整 ZIP 先开放系统文件导出与零写入预览

- 状态：已接受；密码容器由 D-027 扩展，恢复提交继续受限
- 决策：完整 ZIP 导出必须先显示未加密敏感资料与附件风险，再由 Android
  `CreateDocument(application/zip)` 提供输出流并调用 `CaseBackupService.export`。
  导入入口当前命名为“检查完整备份”，由 `OpenDocument` 提供输入流；服务在 App 私有
  临时区执行路径、条目数、展开量、每文件 SHA-256、Schema、数量、领域引用和附件一致性
  校验，显示 manifest 计数后立即清理临时文件。预览不检查目标库是否为空，也不写入或
  提供恢复按钮。现有 `restoreIntoEmptyStore` 能力不从非空主界面直接暴露。
- 原因：真实系统文件往返和完整性预览是恢复前可独立验收的安全子链路；在非空库冲突、
  两阶段附件提交和崩溃恢复日志尚未设计完成时开放“恢复”会制造无范围覆盖或假恢复风险。

## D-027 完整备份密码容器独立版本化并流式处理

- 状态：已接受；密码备份恢复仍受 D-006 与后续非空恢复设计约束
- 决策：完整备份密码保护使用独立二进制容器版本 1 和 `.nfbak` 扩展名。文件由固定魔数、
  有界 JSON 参数头与原始 AES-GCM 密文构成；以 PBKDF2-HMAC-SHA256、600,000 次迭代、
  16 字节随机盐派生 256 位密钥，并使用 12 字节随机 nonce 与 128 位认证标签。容器类型、
  版本、KDF、迭代次数和密码算法进入 AAD，导入仅接受 100,000～2,000,000 次迭代。
  ZIP 输出直接流入加密流，避免完整备份进入内存或 Base64 膨胀；预览先在私有临时区完成
  GCM 认证和解密，再复用原 ZIP 的路径、大小、哈希、Schema、引用和附件校验，最后清理。
  页面只提供系统文件流与临时密码，不解析容器，不持久化密码。
- 原因：完整备份可能包含大量附件，必须保持有界内存；独立协议避免把单命例 JSON 封套
  与 ZIP 恢复语义耦合，同时让错误密码、篡改和参数降级在业务数据解析前统一失败。

## D-028 完整备份先生成零写入逐命例冲突预演

- 状态：已接受；决策编辑与提交仍受两阶段恢复边界限制
- 决策：完整备份通过文件保护、ZIP、哈希、Schema、引用和附件校验后，逐个来源命例与
  当前活动库及回收站比较。相同本地命例的稳定 ID 已存在、出生输入相同和四柱相同原因
  合并为一个候选，并返回本地 revision、删除状态和来源修订号。普通 ZIP 与密码容器共用
  同一预演链。UI 可摘要展示但服务层不得截断；预演不生成默认决策、不写数据库或附件，
  也不开放恢复按钮。
- 原因：批量恢复必须先让用户看到冲突范围，并为后续提交前重新核对建立事实基线；在逐例
  决策、附件事务和过期检测完成前，直接开放恢复会把“已检查”误解成“可安全覆盖”。
