---

## 1. 项目结论

**南枫八字**是一款 Android 本地优先的八字排盘与命例研究工具。

它不是以娱乐测算、会员订阅或在线 AI 为核心，而是以以下四件事为核心：

1. **准确排盘**：四柱、真太阳时、起运、交运和大运结果必须可验证。
2. **命例管理**：保存出生资料、命盘结果、分组、标签、笔记和长期事件。
3. **问真八字截图迁移**：支持单图、多图、长截图和用户列表批量解析，把问真八字中已有的命例资料、命主反馈、师傅点评和排盘字段保真迁移到本地。
4. **长期复盘**：支持事业、婚姻、健康等分析框架、命主反馈、关键事件和人工修正。

第一版只做 Android 手机和折叠屏，不做 iOS、Windows 或 Web；账户体系与云同步为可选的
南枫云能力，不能成为排盘、命例管理或离线使用的前提。

## 2. 产品原则

### 2.1 本地优先

- 核心排盘离线可用。
- 命例、笔记、截图和设置保存在本地。
- 不强制注册账号。
- 不强制联网。
- 不依赖付费模型 API。
- AI 能力只能作为可选外围模块，不能成为核心功能前提。

### 2.2 准确性优先

四柱、生肖、起运、交运、大运出现偏差时，优先修复算法与规则，不允许通过页面层“补丁式改值”。

算法真值按以下层级管理：

```text
公开并版本化的排盘规则
    ↓
天文和历法基础计算
    ↓
南枫八字规则实现
    ↓
双引擎差分测试
    ↓
问真八字等外部软件结果对照
    ↓
人工确认差异原因
```

外部软件结果是重要对照证据，但不能替代可解释、可复现的项目规则。

所有计算结果必须记录：

- 原始输入
- 校正时间
- 所用时区
- 经纬度
- 排盘规则
- 引擎版本
- 规则版本
- 计算时间

### 2.3 年柱生肖产品口径

**南枫八字中的“年柱生肖”必须来自八字年柱地支，并以立春精确交接时刻作为年份分界。**

禁止使用以下错误方案：

- 按公历 1 月 1 日换生肖
- 按农历正月初一换生肖
- 仅按出生年份对 12 取模
- 只判断“立春当天”，不判断立春交接时刻

界面建议显示：

> 年柱生肖：猴（以立春精确时刻为界）

### 2.4 可追溯

图片识别结果、软件计算结果和用户手动修正必须分开保存。

任何导入数据都必须能回答：

- 来自哪张图片
- 哪个解析器识别
- 识别时的置信度
- 用户是否修改
- 软件重新计算结果是否一致
- 当前采用哪一个值

### 2.5 不过度开发

v1.0 不重点投入：

- 旺衰强弱
- 格局判定
- 喜神、忌神
- 大量流派神煞
- 自动预测算法
- 在线社区
- 会员支付
- 云端同步
- 多端协作
- 名人在线数据库

### 2.6 两套验收体系

南枫八字必须把“截图迁移保真”和“排盘算法正确”分开验收。

#### 截图迁移验收

- 问真八字是第一阶段截图格式适配目标。
- 对已声明支持的问真页面，截图中可见内容是迁移保真的来源依据。
- 原图、OCR 原文、结构化结果和用户修正必须同时保留。
- 不得遗漏、串例、静默改写或因单个字段冲突丢弃整张图片。
- 用户确认后的正式数据必须与用户选定的截图内容一致。

#### 排盘算法验收

- 软件计算结果由版本化规则和本地引擎产生。
- 问真四柱、真太阳时、起运和大运作为重要外部对照。
- 差异必须显示输入、规则、引擎版本和可能原因。
- 不允许为匹配单个截图在 UI 或适配层硬编码结果。

### 2.7 隐私与本地数据边界

- 命例、健康、婚姻、财务、反馈和师傅点评均按敏感个人资料处理。
- Android 系统自动备份策略必须显式配置，不得让“本地优先”被系统云备份静默改变。
- 来源图片复制到 App 私有存储后再长期引用，不依赖相册临时授权。
- 日志、测试样本、截图和 Git 仓库不得包含未脱敏的真实命例资料。
- 单命例和完整备份支持用户选择密码加密；未加密导出必须明确提示风险。
- 导出文件名默认使用命例别名或稳定 ID，不强制暴露真实姓名。
- 外部 AI 回填前必须显示将发送的字段，默认允许脱敏且必须由用户主动确认。

## 4. 与问真八字的关系

问真八字是第一阶段的：

1. **现有命例资料迁移来源**
2. **截图格式首要适配目标**
3. **排盘结果重要对照来源**
4. **交互和信息层级参考**

但不得：

- 复制应用名称、图标、商标或素材
- 直接复刻全部视觉设计
- 假设其内部算法规则已经明确
- 为匹配单个命例加入不可解释的硬编码

对已声明支持的问真页面，迁移后的结构化数据必须与用户确认的截图内容一致；这属于截图迁移验收。

四柱、真太阳时、起运和大运则以项目版本化规则为算法真值，以问真八字实际输出作为重要对照，并通过成组边界案例确认。两套验收不得混用。

## 5. 页面结构

### 5.1 底部导航

当前三个主入口：

1. **排盘**
2. **记录**
3. **设置**

底部导航的选中、按压、水波纹和焦点反馈必须由包含图标与文字的完整标签容器承载，不能只在图标背后出现局部色块。

图片建档作为高频动作，可同时放置在：

- 排盘首页
- 命例列表顶部
- 系统图片分享入口

### 5.2 排盘首页

#### 输入卡片

- 姓名
- 性别
- 公历 / 农历
- 日期
- 时间
- 出生地区
- 真太阳时
- 分组
- 保存开关

#### 操作

- 开始排盘
- 图片建档
- 最近命例

“开始排盘”始终可用并直接进入专业细盘；“保存命例”只是持久化选择，不得控制按钮是否
可用或把排盘降级为仅保存动作。关闭保存时生成顶部标明“未保存”的临时详情且零写库；
打开保存时，排盘成功即以同一计算结果进入顶部标明“正在保存”的专业细盘；重复检查和
持久化在后台完成，成功后原子升级为正式详情。不得为了保存、列表刷新或详情回读阻塞
首屏；若发现重复或保存失败，保留原输入并返回新建页给出明确处理入口。

#### 展示原则

- 默认只展示必要字段。
- 经纬度、时区、子时规则放入高级设置。
- 开启真太阳时时，必须显示校正前后时间。

### 5.3 命例列表

记录页顶部按同一列表格式切换“用户列表”“名人案例”和“回收站”。用户命例与名人案例
使用独立案例库类型持久化；名人案例支持当前手动录入，未来文字自动录入必须写入同一类型字段，
不得借用分组或标签模拟归属。

每个列表项显示：

- 姓名
- 性别
- 公历出生日期
- 四柱
- 生肖
- 分组
- 星标或置顶状态

支持：

- 姓名搜索
- 四柱搜索
- 搜索框尾部在筛选按钮左侧提供清字键：单击按完整字符删除末字，长按达到阈值时立即清空，
  不等待松手
- 标签筛选
- 分组筛选
- 最近查看排序
- 出生时间排序
- 创建时间排序
- 修改时间排序
- 用户列表／名人案例切换
- 顶部分组／标签筛选使用紧凑、固定宽高的独立胶囊；选中态只改变内部圆点、颜色和描边，
  不改变控件占位或字重，切换时不得产生横向跳动
- 默认按姓名拼音首字母排序；右侧 A–Z/# 索引在下一组横向字母条进入列表顶部 48dp
  预切换区时提前点亮，切换时对应字母条仍应完整可见
- 活动列表删除写入回收站；回收站内再次选择删除必须永久移除案例及其级联子数据，且不得
  再提示“移入回收站”
- 批量删除编辑条固定提供全选／取消全选、删除、取消；全选只作用于当前筛选后可见案例。
  列表先乐观移除，数据库失败时恢复原投影；大量 ID 在单一事务内分块写入，避免绑定参数上限
- 外部 JSON／备份包只作为导入输入；提交后每个案例及其子记录按独立 `caseId` 持久化，
  日常查看、置顶和删除不得重新读取原始整包
- 置顶、移入回收站和回收站永久删除成功后，先按仓储返回的实际变更数精确更新内存目录投影；
  正常路径不得重新查询整库。变更数不一致时允许静默校准，但已有列表必须保持可见
- 全屏“正在读取命例”只允许用于首次进入且内存中没有任何列表内容的状态；已有列表或详情
  在后台刷新时不得被加载页遮盖。普通详情首次打开只读取一次完整聚合，最近查看时间本地
  精确回写；再次打开同一案例先显示保留详情，再静默校准

记录页顶部工具区以及搜索框、筛选胶囊、分组按钮之外的空白区域使用低饱和浅灰页面底；
搜索框、按钮和完整列表内容区使用纯白。右侧 A–Z/# 竖向索引所在区域保持纯白，只有随列表
内容出现的横向 `# / A / B…` 分组条使用浅灰划分，并整行贯穿右侧索引下方。顶部案例库分段控件仅保留极浅中性灰，
数量使用低一级字号。三点溢出菜单保持原有自适应尺寸与位置，只把静止承载面统一为纯白。

### 5.5 图片导入确认页

图片导入确认页是一个可恢复的迁移工作台，不是一次性弹窗。

#### 普通手机

- 顶部：导入进度、页面类型和命例归组
- 上方：原始截图
- 下方：结构化字段、长文本和冲突
- 点击字段后定位截图区域

#### OPPO Find N5 展开状态

- 左侧：原图、图片列表和截图定位
- 右侧：命例候选、字段、长文本、校验和修改
- 底部：创建命例 / 补充命例 / 暂存待核对

每个字段显示：

- 识别值
- OCR 置信度
- 字段解析置信度
- 来源图片
- 软件计算值
- 是否一致
- 用户最终选择

批量导入必须显示：

- 当前批次图片数量
- 已识别、待确认、冲突、失败和已完成数量
- 每个命例候选包含的图片
- 新建、补充、重复和疑似串例状态
- 失败原因、重试、移出批次和暂存操作

退出页面或 App 重启后，未完成导入会话不得消失。

## 6. 技术选型

### 6.1 Android

- Flow
- Room

### 6.2 OCR

优先采用可在 Android 端离线运行的中文 OCR。

第一阶段先做技术验证，不提前锁死具体库。候选顺序：

1. ML Kit 中文 bundled 模型：作为第一套 Android PoC。
2. PaddleOCR 或 RapidOCR：作为小字号表格和长截图的准确率对照。
3. 只有对照样本证明明显更优时，才承担更大的模型、包体和端侧集成成本。

评估标准：

- 简体中文识别
- 小字号表格识别
- 长截图
- 字符边界框
- 端侧离线
- 模型体积
- OPPO 设备兼容性
- 批量图片性能

必须通过 `OcrEngine` 接口隔离具体实现。

```kotlin
interface OcrEngine {
    suspend fun recognize(image: ImportImage): OcrDocument
}
```

Photo Picker 或系统分享提供的 URI 可能只有临时权限。需要保留来源图片时，导入入口必须先复制到 App 私有存储，再把内部引用交给后台任务。WorkManager 只传递内部图片 ID，不传递大图 Bitmap。

## 7. 架构方案

### 7.1 原则

- UI 不直接调用 Tyme4j。
- OCR 不直接写数据库。
- 导入结果不直接覆盖正式命例。
- 计算结果和外部截图结果分开。
- 规则配置可版本化。
- 核心数据模型不依赖 Compose。
- 先按包划分边界，边界稳定后再拆更多 Gradle 模块。

### 7.3 计算引擎接口

```kotlin
interface BaziEngine {
    suspend fun calculate(
        input: BirthInput,
        profile: CalculationProfile
    ): CalculationResult
}
```

`CalculationResult` 在一次调用中原子返回：

- 规范化后的出生输入
- 时间校正过程
- 四柱和基础排盘
- 起运、交运和大运
- 所用规则、引擎和数据版本
- 警告、输入不确定性和可追溯证据

正式实现：

```text
TymeBaziEngine
```

测试实现：

```text
FakeBaziEngine
ReferenceResultComparator
```

未来若更换底层算法，UI 和数据库不需要推翻。

Tyme4j 的 `ChildLimit.provider` 属于进程级可变状态。适配层不得让不同 `CalculationProfile` 并发修改该状态；阶段 0 必须用串行隔离和恢复测试证明规则不会串用，或在项目内建立无全局状态的起运规则包装。

### 10.5 字段来源

每个字段保存：

```kotlin
data class ExtractedField(
    val key: FieldKey,
    val rawText: String,
    val normalizedValue: FieldValue?,
    val ocrConfidence: Float?,
    val parserConfidence: Float,
    val consistencyConfidence: Float?,
    val imageId: String,
    val boundingBox: Rect?,
    val parserRuleId: String,
    val userEdited: Boolean
)
```

其中：

- `rawText` 永远保存截图原文。
- `normalizedValue` 使用按字段类型约束的值，不能让所有字段长期退化为字符串。
- OCR、字段解析、多图一致性和本地重算一致性分别记录，不能合并成一个模糊分数。
- 用户修改生成新的采用值，不覆盖原始 OCR 证据。

### 10.6 数据合并规则

多张截图合并时：

- 同一字段相同：提高置信度。
- 同一字段不同：标记冲突。
- 一张图为空：使用另一张图。
- 四柱与出生时间不匹配：保存导入会话和来源证据，但阻止冲突字段晋升为正式命例真值。
- 姓名、四柱、出生时间和页面头部高度一致：生成“疑似同一命例”候选，不自动合并。
- 只有姓名相同：不能自动合并。
- 用户列表页一张图中的多行必须生成多个独立候选，不能被批次总状态绑在一起。
- 单个命例冲突不阻止同批次其他命例完成。
- 原文件哈希完全一致可以判定重复；感知哈希相似只能提示，不得自动删除或合并。

命例身份候选至少显示以下依据：

- 姓名是否一致
- 性别是否一致
- 公历或农历出生时间是否一致
- 四柱是否一致
- 来源页面头部是否一致
- 哪些图片和字段存在冲突

### 10.7 结果对照

```text
软件计算：壬申 戊申 壬申 丙午
截图识别：壬申 戊申 壬申 丙午
状态：一致
```

不一致时显示：

- 差异字段
- OCR 置信度
- 原图位置
- 软件输入
- 排盘规则
- 可能原因

禁止自动采用截图结果覆盖软件计算结果。

同时也禁止因软件计算结果不同而删除或改写截图来源值。三类值必须独立：

```text
截图来源值 SourceObservedValue
软件计算值 CalculatedValue
用户采用值 AdoptedValue
```

### 10.8 长文本和时间线保真

命主反馈和师傅点评的首版目标是“完整迁移”，不是“自动理解全部命理观点”。

- 师傅点评优先保存为一个完整 `AnalysisSection`，保持原有段落顺序。
- 命主反馈按截图中的年份或日期生成 `CaseEvent` 候选，同时保存覆盖整页的完整原文记录。
- 年份、干支、事件状态和正文必须分开建模；无法确定时保留原文并标记待核对。
- OCR 无法可靠分段时，不得为了结构化而截断、重排或改写原文。
- 用户修正年份或正文时保留原始 OCR、修改前值和来源图片定位。
- 长截图分段必须在原始分辨率上进行，相邻分段保留重叠区域并在合并时去重，不能整体缩小后识别小字。

### 11.2 分析框架

- 性格
- 事业
- 财运
- 婚姻感情
- 健康
- 学业
- 家庭

- 用户手写

- 版本记录

任何 AI 结果必须明确标记来源，不得与软件确定性计算混在一起。

### 11.3 AI 命盘分析指令

- 基本排盘底部提供本地 AI 指令入口，自动读取当前唯一采用快照对应的客观摘要。
- 支持全项、事业、财运、婚恋、子女、六亲、健康和学业八种分析主题。
- 默认隐去姓名和地区类身份信息，保留排盘必要的性别、出生时间、四柱、十神、藏干、起运与大运；可预览完整提示词后由用户主动复制。
- 指令将盲派命理单列为实际断事路径，再与子平格局和常见现代方法交叉核对；同时要求第三方模型区分输入事实与推演、说明不确定性，并在开头和结尾保留传统文化娱乐参考声明。
- 复制成功后弹窗立即关闭；复制失败时留在原位并显示可执行错误，不让成功路径多一次关闭操作。
- 该“复制 AI 指令”入口自身不联网、不自动发送，也不把外部回答写回排盘结果；需要手动保存外部回答时继续使用已有外部分析桥接。

### 11.4 内置 AI 点评

- 断事笔记在“师傅点评”右侧提供独立“AI 点评”模式；未生成时也必须直接显示完整编辑框，
  允许手动输入或粘贴用户自行生成的 AI 点评。占位提示只作提示，不写入真实内容。
- 师傅点评与 AI 点评编辑框使用同一底线和剩余空间分配，正文超出后在框内上下滚动，右侧显示
  轻量滚动条；两页底部都固定显示同一保存区。界面不展示“固定结构”等底层实现说明。
- 默认提供 OpenRouter、DeepSeek、千问三家 OpenAI 兼容服务；每家使用当前主流模型预设选择框，普通流程不手填模型名，官方接口地址由程序固定且不在界面暴露。API Key 仅在当前设备使用 Android Keystore 加密保存，输入框可通过小眼睛显示或隐藏。
- 每次生成前显示发送范围并要求主动确认；默认隐去姓名、别名、地区、经纬度与时区，但保留排盘所需的出生时间、性别口径、四柱、十神和岁运。
- 输出固定为核心判断、盲派断事观察、子平交叉核对、事业与财运、婚恋与六亲、健康提示、关键阶段、待核验问题、依据与不确定性九个信息组。
- 生成结果先进入可编辑预览，不自动保存；确认保存后新增带服务、模型、提示版本、资料编号、生成时间和用量的外部 AI 分析记录，不覆盖师傅点评或本机计算结果。
- AI 模型服务为独立子页面；“模型设置／调用记录”使用横向充分展开、在剩余页面中垂直居中的
  两张入口卡片，避免局促堆在顶部；进入后仍分别打开对应弹层。

```text
南枫八字备份_YYYY-MM-DD_HHmm.zip
```

结构：

```text
manifest.json
cases.json
groups.json
tags.json
snapshots.json
notes.json
analysis.json
events.json
settings.json
imports.json
attachments/
```

`manifest.json` 至少记录：

- 备份格式版本
- App 版本
- 数据库 Schema 版本
- 引擎和规则版本
- 创建时间
- 每个文件的相对路径、字节数和 SHA-256
- 命例、快照、记录、事件和附件数量
- 是否加密及加密参数版本

未加密 ZIP 必须在导出前提示其中可能包含出生资料、健康、婚姻、财务、反馈和来源图片。密码加密备份不能把密码或可恢复密钥写入同一个 ZIP。

### 12.3 导入流程

1. 读取文件
2. 校验路径安全、文件大小和压缩展开上限
3. 校验每个文件哈希
4. 校验 Schema、备份格式和版本兼容性
5. 显示备份版本、加密状态和来源信息
6. 显示命例、记录和附件数量
7. 检测重复和冲突
8. 导入临时数据库和临时附件区
9. 运行引用、哈希和完整性检查
10. 显示逐命例预览和冲突方案
11. 用户确认
12. 通过两阶段提交迁移数据库与附件
13. 提交失败自动回滚，保留可诊断原因
14. 重启 App 后复查数据和附件均可读取

冲突选项：

- 跳过
- 保留两份
- 按模块合并
- 逐字段采用来源值或本地值

“覆盖”不能作为无范围的快捷选项。任何替换必须明确到命例、出生输入、快照、记录、事件或附件，并在确认页显示会失去什么。

## 17. Git 与文档规范

仓库初始结构：

```text
docs/
├── PRODUCT_REQUIREMENTS.md
├── ARCHITECTURE.md
├── DECISIONS.md
├── TEST_STRATEGY.md
├── GOLDEN_CASES.md
├── IMAGE_IMPORT_SPEC.md
└── CHANGELOG.md
```

开发要求：

1. 修改前先检查 Git 状态。
2. 重要修改前提交现有工作。
3. 每次只解决一个明确问题。
4. 先写失败测试，再修改算法。
5. 不同时修改算法、OCR 和 UI。
6. 不在页面层修正算法结果。
7. 不删除旧实现，除非新实现已验证且有提交可回滚。
8. 重要决策同步写入 `DECISIONS.md`。
9. 数据结构修改必须有迁移测试。
10. 备份恢复功能必须有端到端测试。
11. Codex 不得擅自更换技术栈或推翻现有架构。
12. 任何大规模重构先提交方案，不直接动代码。

## 20. 开源项目参考边界

### 可直接研究和使用

- [`6tail/tyme4j`](https://github.com/6tail/tyme4j)：MIT，Android/JVM 主历法、四柱、童限和大运底座；真太阳时、时区和可变 provider 由适配层治理。
- [`6tail/lunar-java`](https://github.com/6tail/lunar-java)：MIT，只用于差分测试和边界对照，不作为第二套生产真值。
- [`RedSC1/bazi_core`](https://github.com/RedSC1/bazi_core)：MIT，参考真太阳时、子时、岁运结构和测试；不为此引入 Flutter/Dart 运行时。
- [`RedSC1/opendestiny-flutter`](https://github.com/RedSC1/opendestiny-flutter)：MIT，参考命例模型、地点库、JSON 迁移和信息层级；不复制 Flutter 实现和视觉资产。
- [`hhszzzz/taibu/packages/core`](https://github.com/hhszzzz/taibu/tree/master/packages/core)：MIT，只参考结构化协议和分析模块。
- [`PaddlePaddle/PaddleOCR`](https://github.com/PaddlePaddle/PaddleOCR)：Apache-2.0，作为端侧中文 OCR 的第二套准确率基准。
- [`android/nowinandroid`](https://github.com/android/nowinandroid)：Apache-2.0，参考 Room、Flow、数据真值和测试分层，不照搬其完整模块规模。
- [`android/compose-samples/Reply`](https://github.com/android/compose-samples/tree/main/Reply)：Apache-2.0，参考手机、平板和折叠屏列表—详情自适应布局。

### 需要避免

- 直接复制问真八字视觉资产和品牌。
- 复制 Taibu 根应用的 AGPL-3.0-only 代码；只有带独立 MIT `LICENSE` 的子目录按其子目录许可证使用。
- 复制 [`destinynet/destiny-core`](https://github.com/destinynet/destiny-core) 的 GPLv3 代码；该项目只作为 Kotlin 命理领域设计和测试思路参考。
- 把未经验证的神煞或 AI 录入规则作为正式计算标准。
- 同时接入多套正式引擎造成结果来源混乱。
- 把开源项目 README 中的“精准”表述直接当作南枫八字验收证据。
