## 2. 项目目标与产品边界

南枫八字是本地优先的 Android 命例研究工具：出生资料录入与排盘、专业细盘、断事笔记/事件、记录分类检索、万年历、合盘、资料导入导出、备份，以及可选 AI 点评和加密云备份。

排盘准确性与资料迁移是两套验收任务。外部截图中的来源值、本机计算值和用户采用值分别保留；来源不完整或矛盾时不得拼造确定结果。AI 点评和命理派生分析不能覆盖出生输入、计算档案或用户原文。

依据：[产品需求](PRODUCT_REQUIREMENTS.md)、[领域规则](domain-rules.md)、[数据合同](DATA_CONTRACT.md)、[云合同](cloud-sync-contract.md)，以及 `CaseModels.kt`、`WenzhenSourceFidelityContract.kt`、`CaseObjectiveSummary.kt`。

## 4. 架构、所有者与数据流

`DefaultAppContainer` 是手工依赖组装点，创建 Room、引擎、仓储、目录投影、导入、备份、AI 与云协调器；`MainActivity` 处理系统入口，`StageTwoViewModel` 组织主要 UI 状态与用例，Compose 展示这些状态。

| 概念 | 唯一主要所有者 | 约束 |
| --- | --- | --- |
| 四柱/计算档案 | BaziEngine / TymeBaziEngine | 保存输入、规则配置、引擎版本和计算结果 |
| 专业岁运事实 | ProfessionalFortuneResolver / TymeProfessionalFortuneResolver | 交节、换日、交运与父区间由引擎解析，UI 不复算 |
| 命例聚合写入 | CaseRepository / RoomCaseRepository | expectedRevision 与单事务；增量用例不直写 DAO |
| 完整备份/恢复 | CaseBackupService | 特权批量恢复在数据层事务中执行，不由页面绕过仓储 |
| 单命例交换 | SingleCaseExchangeService / SingleCaseBundleService | 预览、冲突、密码、附件与提交分别建模 |
| 可恢复目录 | RepositoryCaseCatalogStore | 可丢弃读取投影；Room 仍为真值 |
| 详情与草稿 | StageTwoViewModel | 绑定 caseId + revision；原子装载子状态 |
| 截图识别 | ImportRecognitionCoordinator、ScreenshotImportViewModel/Committer | 可恢复会话、证据确认与提交分离 |
| 云备份 | BaziCloudSyncCoordinator + CaseBackupService | 本机源、结构化加密快照、账号隔离 |

### 4.1 录入与排盘

表单/农历/四柱反查 → `BirthInput` 与 `CalculationProfile` → `BaziEngine.calculate()` → 预览 → 显式保存 → `CaseRepository.save()` → Room 聚合/采用快照 → 列表及详情。即时预览不是保存成功，四柱反查候选必须正向复核。

### 4.2 记录和详情

内存或磁盘目录投影 → 首屏 → 仓储静默校准。维护任务和异步写盘不阻塞已有内容发布；写盘串行锁与内存锁分离，代次守卫防止旧快照覆盖新快照。详情缓存也只能加速，不证明笔记/事件不存在。

案例选择 → 聚合及 revision 校准 → 详情四标签 → 专业岁运观察时刻/选择状态。标签切换仅改变呈现；专业视口随案例保存，宽窄布局返回不隐式清空。长图临时展开同一真实渲染器，finally 恢复原标签、浏览模式和状态。

### 4.3 外部资料

系统 URI → 私有副本 → 分块/指纹/识别 → 页面分类、资料归组、字段证据 → 人工核对 → ScreenshotImportCommitter → 仓储。image-parser 保留 ML Kit 实现，但当前生产容器注入的是 `AiVisionScreenshotOcrEngine`；不能把截图识别整体写成离线功能。

### 4.4 备份与外部能力

完整备份：Room 聚合 → 流式 JSON 与附件清单 → ZIP/哈希 → 可选密码封装。恢复：校验/临时数据库预演 → 显式逐例计划 → 再认证文件与 revision → 事务/附件提交与 journal → 中断恢复或拒绝。

AI：用户选择服务和发送范围 → HTTP 生成 → 可编辑点评 → 保存版本与调用记录；密钥以 Keystore 管理的 AES-GCM 密钥加密后存私有偏好。

云：Google 身份/恢复码确认 → 加密结构化快照 → 按 App 隔离文档与版本提交。已有本机命例以本机为备份源；空白设备在解锁后恢复；退出保留本机业务数据。用户启用后的表失效触发 30 秒合并任务，12 小时周期兜底，不要求每个后台任务再次点击。

## 12. 已知问题、验证缺口与后续路线

### 已确认的限制/风险

- 真太阳时应用规则仍为 PROVISIONAL；外部问真边界对账缺失不能由内部差分消除。
- 构建产物默认名称落后内部版本；APP_BUILD_TIME导致重建哈希漂移。交付需冻结实际产物。
- 两个主要app文件体积大；这是维护风险判断，尚无证据表明按文件拆分即可解决帧问题。
- 缺少本轮真实AI/Google/Supabase、跨设备解锁与恢复证据；历史覆盖安装只证明所核验的身份/包和数据目录保持。
- 真实问真包对账跳过；schema1无已提交JSON但迁移测试显式构造v1，不能将测试构造等同所有历史用户库验收。
- 无全量真机操作性能验收/覆盖率；已有慢帧与采样边界仍保留，不承诺所有环境零延迟。

### 有依据的后续验证路线（不是新增功能承诺）

1. 根据 TEST_STRATEGY 和当前验证缺口，先补真实问真/真太阳时边界对账与必要目标设备交互证据；真实服务单独授权。
2. 在确需下一次构建时，定向处理产物命名一致性，并保留同身份、版本、哈希与数据保持的交付门禁。
3. 如继续重构大型app编排，按唯一所有者和垂直链路拆分，每步保持聚合、取消、导航/导出恢复及现有测试；不能仅按文件行数迁移业务。
