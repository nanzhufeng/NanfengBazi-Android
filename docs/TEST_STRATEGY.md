# 测试策略

## Stage 0 门禁

1. 领域模型测试：输入校验与版本字段不可省略。
2. 引擎公开样本：四柱必须与 Tyme4j 公共测试一致。
3. 节气边界：立春前一秒与交节瞬间的年柱必须不同且符合预期；专业流月对多年份十二
   “节”验证交节即切换，对十二“气”验证不切换。
4. 子时边界：22:59、23:00 与 00:00 同时覆盖 Tyme 默认和晚子时口径，验证只有
   23:00–23:59 的日柱存在规则差异，且调用不污染全局 provider。
5. 状态隔离：每次计算后恢复 Tyme4j 全局 provider。
6. 配置隔离：不同起运配置不得污染后续计算。
7. 全仓测试与 Debug 构建：`./gradlew test assembleDebug`。

## 证据分级

- L1 静态：结构、依赖、敏感信息扫描。
- L2 自动化：单元测试通过。
- L3 构建：Debug APK 成功生成。
- L4 设备：真机安装与启动。
- L5 业务：真实问真截图迁移及逐字段验收。

Stage 0 的目标仅到 L3；L4、L5 未执行时必须明确标注。

## alpha72 问真式 UI 与来源模型门禁

1. 首页、记录、设置三个根入口必须继续调用现有 ViewModel/用例；视觉重排不得
   复制排盘、反查、搜索、导入或备份逻辑。
2. 记录密集行必须从命例聚合与唯一已采用快照读四柱；彩色字、生肖圆标与
   A–Z 索引只做展示，改版后必须完成“保存—搜索—进详情—返回”真实 UI 流。
3. 详情四标签切换必须保留黑金身份头；基本排盘表只读已采用快照，管理动作
   默认折叠后仍须能被自动测试明确展开。
4. 每个有点击语义的分段项和导航项必须至少 48dp。alpha72 在 API 35 实际发现
   性别分段宽度只有约 44.5dp，修正为 `widthIn(min = 48.dp)` 后必须重跑全页语义审计。
5. Room v7→v8 必须新增非空 `sourceType`；无附件历史记录归一为 USER，有来源附件者
   归一为 IMPORTED_IMAGE。备份/单例往返、修订历史和外部分析回填必须保留该值。
6. 冻结集 schema v2 的 60 条样本必须显式标记性别、时间精度、来源和验证级别；
   缺少真实问真外部证据时必须写明不可用，不能用“60 条”冒充真实案例验收。
7. 当前 API 35 定向证据：三主入口、VX-09 Activity 重建、保存案例进详情共
   3/3 通过；48dp 可访问性审计 1/1 通过。这只是 `emulator-5554` API 35 证据，
   不代替 OPPO、真实资料、正式签名或发布。

## Stage 4A 算法回归门禁

1. `four-pillars-golden-v2.psv` 至少保留 50 个冻结样本，当前为 60 个，输入和四柱期望
   不得在同一修复中无解释地同时改写。
2. 样本覆盖 1900–2200、闰日、立春前后日期、常用历史日期和多个时辰；农历、闰月、

   `lunar-java 1.7.7` 参考实现；任一差异都需要先分类规则口径，禁止直接更新期望值。

## Stage 5A 图片导入基础设施门禁

1. Photo Picker 与系统分享 URI 必须先流式复制到 App 私有目录；后台与 OCR 只读取内部
   图片 ID/相对路径，不长期依赖外部 URI。
2. 私有复制必须限制大小与路径，计算 SHA-256，以临时文件加原子移动提交；失败不得留下
   可被误认成完整图片的目标文件。
3. 导入会话必须通过 Room 修订号与显式状态迁移持久化；失败、识别中断和待核对状态在
   进程重建后可见，重试复用已校验原图。
4. OCR 引擎必须声明 `OFFLINE`；首个 ML Kit 中文模型使用 bundled 依赖。最终 Debug 与
   Release 合并 Manifest 均不得包含 `INTERNET`、`ACCESS_NETWORK_STATE` 或动态模型
   下载 metadata。
5. 页面分类必须同时命中页面主锚点与辅助锚点；允许版本化繁简归一化，但原始 OCR 文本
   永不覆盖。单一关键词必须保持 `UNKNOWN`。
6. API 35 模拟器使用程序生成的合成问真列表图，真实经过分享入口、私有复制、bundled
   OCR、页面分类和 Room 会话，并验证正式命例库仍为空。
7. 超过单次像素阈值的合成长图必须走重叠分段；底部文字边界框应回映到原图坐标，重叠
   文字不得形成重复证据。
8. 每张可解码图片保存宽高与 64 位 dHash；SHA-256 完全重复和低汉明距离视觉相似必须
   分开提示，任何一种都不得自动合并命例。
9. 批次中单张识别失败不得丢弃成功图片；逐图失败结果跨 Room 往返保留，局部重试不得
   重复 OCR 已成功图片。
10. OCR 由会话 ID 对应的唯一 WorkManager 任务执行，最终 Manifest 仍不得恢复网络权限；
    合成设备链必须经过真实 Worker，并验证确认删除后 Room 会话和私有原图同时消失。
11. 多图归组必须覆盖横排/上下两行四柱、姓名加日期、仅同名、身份字段冲突和用户列表
    隔离；只有强身份信号全组两两成立才允许形成多图候选，且仍需人工核对。
12. 获得用户逐批授权的真实用户列表后，指标必须分层报告页面分类、日期行候选、姓名/
    性别规范化、四柱完整规范化和同日正向复算，不得把某一层成功冒充整例全自动成功。
13. 用户列表姓名块漏识别时，可靠公历日期行仍须保留独立、可定位、可人工修正的候选；
    不得复用上一行身份，不得因空行令整图失败。
14. 没有精确出生时间的列表候选提交时，必须分别经过两种子时口径反查、同日过滤和
    `BaziEngine.calculate()` 正向复算；无解显式拒绝，保存候选均为
    `DOUBLE_HOUR_ONLY`，页面固定显示非唯一出生分钟说明。
15. 用户列表精识别必须覆盖带括号或句点姓名、姓名/性别分块、首次 OCR 漏日期、重复
    日期锚点、单块/整行/逐列四柱、六十甲子非法组合和来源星号隐去。二次日期扫描不得
    覆盖已有日期；四柱不得跨 OCR 块拼接，空间证据必须天干/地支同列一一配对。完整
    OCR 四柱须在两种子时口径下核对同日；冲突形成复核警告，不能绕过正式提交门禁。

以上证据只说明基础设施和合成图链路成立，不得替代真实问真截图的分类、OCR、字段迁移
准确率验收。

## Stage 1 门禁

1. 字段语义：未提供、已有值、用户清空可以无损往返。
2. 写入并发：旧修订不能覆盖新修订，重复稳定 ID 不静默覆盖。
3. 关联完整性：记录、事件和字段证据只能引用当前命例附件。
4. 顺序保真：同一时间的反馈和点评仍按来源顺序读取。
5. Room 迁移：v1→v2 保留原命例并补齐来源类型与顺序字段。
6. 备份往返：数据库和附件恢复后事实与字节一致，再导出结果确定。
7. 防御性恢复：路径穿越、文件篡改、非空目标和密码降级均被拒绝。
8. 失败回滚：附件提交失败后，空库写入全部撤回。

Stage 1 仍只达到自动化和构建证据；没有设置页、系统文件选择或真实设备恢复证据。

## Stage 2 门禁

1. 表单校验：别名、性别和完整有效公历时间缺失时给出明确中文原因。
2. 唯一链路：有效输入只经过 `BaziEngine.calculate()` 和
   `CaseRepository.save()`，并保存采用的版本化计算快照。
3. 结构化失败：计算失败、稳定 ID 已存在、修订冲突和数据库异常均不静默失败，
   且数据库异常后表单输入保留。
4. 列表读取：姓名/别名搜索返回出生输入和已采用四柱摘要。
5. 详情读取：导航参数指向仓储稳定 ID，页面区分原始录入与计算结果。
6. 导航连续性：新建、详情和系统返回均回到手机单列列表。
7. 模拟器 UI：使用合成资料和真实 Room + Tyme4j 完成
   新建→保存→搜索→详情；不把该证据冒充 OPPO 真机或真实问真资料验收。

Stage 2 自动化覆盖表单、用例、ViewModel、导航、仓储摘要接线和 Compose UI 冒烟。
OPPO 真机安装、进程重启后的持久读取及真实问真迁移仍需独立验收。

## Stage 3A 增量门禁

1. 编辑重算：旧修订在调用引擎前被拒绝；成功后旧快照保留且仅新快照采用。
2. 三态姓名：编辑时清空已有姓名保存为 `CLEARED`，不能改写为 `ABSENT`。
3. 文本记录：四种记录支持新增、修改和确认后删除；稳定 ID、创建时间、顺序、
   九类分析分类和新增/修改/删除版本均保留。
4. 关键事件：可选标题、八类类别及未知/年/月/日四种精度可保存；非法日期和超长标题
   不得写入；旧事件首次修改自动补建基线，删除后历史继续可读。
5. 聚合并发：每次记录/事件更改携带详情修订号，冲突时保留编辑输入。
6. 数据回归：Room、备份、迁移和附件测试全部继续通过；Schema v7 必须从旧版
   无损迁移，备份格式 v1 以默认空历史兼容旧文件，空库恢复语义不变。
7. 模拟器 UI：真实 Room + Tyme4j 完成创建→编辑重算→新增及修改分类分析→读取旧版本
   →新增带标题/类别事件→详情与历史读回。
8. 管理元数据：分组/标签同名复用、数量/长度校验、收藏/置顶往返均有用例。
9. 查询契约：姓名/别名/四柱搜索、分组/标签筛选、置顶优先和四种排序由仓储测试。
10. 最近查看：只更新查看时间，不提升 revision；写入失败仍允许读取详情并明确提示。
11. 可恢复删除：活动列表隐藏、回收站可见、恢复后稳定 ID、记录、事件、快照和附件
    引用保持不变；回收站浏览不更新最近查看。
12. 命例复制：新命例和快照使用新 ID，保存来源 ID；记录、事件、附件和字段证据不复制。
13. 重复候选：出生身份和四柱理由分别验证；确认前零写入，活动与回收站位置可见。
14. 模拟器 UI：在已有持久数据下完成重复确认→编辑→复制→移入回收站→检索→恢复。
15. 历史保真：当前条目删除、整例软删除/恢复和完整备份恢复均不得丢失记录或事件历史；
    研究副本则明确清空记录、事件及其历史。
16. 命例列表工具栏必须保留用户列表／回收站、搜索、分组／标签筛选、四种排序和更多菜单的原功能；主要触控目标不得小于 48dp。筛选开关折叠后筛选条不存在，再次点击恢复；排序控件必须直接显示当前排序名称。
17. 交互形状合同：带圆形、胶囊或圆角表面的控件必须由同一形状所有者裁切按压／水波纹反馈；优先使用可点击 `Surface/Card`。手写 `Modifier.clickable` 只允许先显式 `clip(shape)` 的自绘控件或登记过的真实矩形行／遮罩，新增入口由 `InteractionShapeContractTest` 阻断。

永久物理清理不属于当前增量；在附件引用计数、用户备份和失败恢复策略完成前不提供入口。

## Stage 3B 增量门禁

1. 单命例 JSON：格式、App、数据库版本、导出时间、附件模式、完整聚合和规范载荷
   SHA-256 必须进入 v1 封套。
2. 未加密导出必须由调用方明确确认敏感数据风险；密码模式不得降级为明文，且加密输出
   不得出现命例别名、记录正文等明文片段。
3. 未加密文件与解密后 JSON 上限为 16 MiB，加密容器上限为 24 MiB；非法 JSON、未知
   格式/数据库版本、非法领域引用和载荷哈希不一致必须在冲突查询前拒绝。
4. 预览只读取本地稳定 ID、出生输入和四柱候选，不写命例、附件或历史。
5. 单 JSON 的附件模式固定为 `REFERENCES_ONLY`；不得把引用元数据冒充已携带图片二进制。
6. “跳过”必须零写入；“保留两份”必须重建聚合全部稳定 ID，保留来源 ID，且不得覆盖
   任何本地命例。
7. 提交前必须重新查询冲突；预览结果变化时返回 `PREVIEW_STALE`，不得沿用过期决策。
8. `REFERENCES_ONLY` 命例存在附件引用时必须返回 `ATTACHMENT_BINARIES_REQUIRED`，
   不能提交产生缺失文件的证据引用。
9. 模拟器 UI 必须真实经过 Android 创建文档→写入→打开文档→同文件预览→保留两份
   提交，并从列表读回第二份，证明不是内存流或仅界面演示。
10. 模块合并只追加内容签名不同的快照、记录、事件、分组和标签；所有新增子项重建 ID，
    来源快照默认不采用，相同内容不得重复追加。
11. 逐字段差异默认选择本地；只有明确采用来源的字段可替换。目标 revision 或规范载荷
    在方案生成后变化时必须返回 `TARGET_CHANGED`。
12. 模拟器同一真实文件还必须选择本地目标、勾选记录/事件模块并完成 Room 更新，再次
    打开文件继续保留两份，证明两类提交可以连续执行。
13. 密码容器必须覆盖无密码、错误密码、正确密码、密文篡改、KDF 参数降级/超限及
    解密后协议篡改；模拟器必须真实经过创建文档→密码导出→打开同一文件→密码预览，
    且预览阶段跳过后数据库零写入。
14. 完整 ZIP 必须先确认未加密风险，再通过 Android 创建文档写出；只读预览必须经过
    Android 打开文档，对路径、大小、SHA-256、数量、引用和附件一致性执行完整校验，
    在当前数据库非空时仍保持零写入且不显示恢复按钮。
15. 完整备份密码容器必须流式加密 ZIP，不在内存中整包 Base64；覆盖无密码、错误密码、
    正确密码、密文篡改和 KDF 参数降级/超限。模拟器必须真实创建并打开同一 `.nfbak`，
    通过认证后再执行原 ZIP 全部校验，关闭预览仍保持数据库零写入。
16. 完整备份冲突预演必须合并稳定 ID、出生输入和四柱原因，包含本地 revision 与回收站
    状态；至少覆盖不同稳定 ID 的同出生/同四柱候选。普通 ZIP 与密码容器都必须在模拟器
    显示冲突摘要，预览前后数据库事实完全一致。
17. 完整恢复计划必须覆盖全部来源且每例恰有一个显式决策；验证无冲突直接导入、冲突
    直接导入拒绝、跳过、保留两份限制、合并目标/空范围限制，以及本地 revision 变化后
    `PREVIEW_STALE`。计划生成阶段不得写数据库或附件。
18. 完整备份解析出的每个来源预览必须与原 Room 聚合重建后的 `BaziCase` 完全相等，包含
    记录/历史、事件/历史、快照、附件、字段证据、分组和标签；不能只验证摘要字段。
19. 完整备份预览和提交重读必须把完整 `RoomDataSnapshot` 写入独立临时 Room 数据库，
    再完整读回并重建领域聚合；临时库约束、实体或领域往返失败时正式库保持零写入。
    API 35 系统 ZIP 工作台必须显示“独立临时数据库预演：通过”。
20. 完整备份对冲突目标的合并分析必须与单命例共用实现；覆盖过期/非候选/回收站拒绝、
